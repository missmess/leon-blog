移动端跨端技术的演进

经验总结

阅读15分钟

# 跨平台# 前端# Uniapp# Android端# iOS端# 架构

概要：本文介绍的内容包括移动端跨端技术的发展史、现状、以及常用跨端框架的底层原理。

从移动互联网初期开始，“跨端”就出现在了大家的视野之中。并伴随着移动互联网的蓬勃发展，新的跨端技术更是层出不穷，不断地将跨端应用的体验往极致的方向迈进。未来必然会有更多变化，完美的解决方案可能永远不会到来。但是，了解每一种技术，了解它们出现的历史背景和意义，对于一位跨端开发者，将会更好的把握未来的方向。

H5

移动互联网早期，原生的Android、iOS应用非常流行。但是很快大家就感受到了问题所在：原生开发动态性不足，各种bug的修复和功能的迭代都需要依赖于App更新；此外，任何功能都需要Android和iOS开发者都实现一遍，效率很低下。

好在Android和iOS都支持WebView，方便在App内展示Web应用。Web的灵活性和跨平台特性解决了不少的问题。在这一时期，开发者需要做的重要的工作就是页面的适配。保证自己的Web页面在不同的设备上都有良好的体验。

代表技术：仅用WebView加载H5应用的套壳App。

当然H5应用的两大问题非常明显：

  • 性能问题：纯H5应用的页面加载依赖网络，白屏时间过长。

  • 底层能力：纯H5应用只能使用WebView提供的浏览器能力，能力很有限。无法调用大部分系统底层能力。

为了解决这两个问题，聪明的开发者提出了Hybrid。

Hybrid

Hybird强调的是Web与原生相结合的混合开发模式。

对于H5应用的两个问题，Hybrid可以这样解决：使用离线包、缓存等方案，优化Web应用的加载性能；通过JsBridge来实现Web与原生Api的相互调用。

代表技术：Cordova、HTML5+。

原理

从架构层面考虑。Hybrid技术仍然使用WebView作为渲染引擎，并通过对WebView的封装实现离线化、缓存等能力。同时增加一个原生的中间层SDK，对Android和iOS等平台的原生Api进行封装。这个中间层最终通过JsBridge来暴露封装后的Api到Web端，从而实现双向调用。整体的架构图如下：

限制

Hybrid技术到如今仍然大量在使用，这是因为它的实现成本很低。当然，Hybrid并不完美。它也存在着不少的问题：

  • 加载速度、交互体验、动画效果等，对比原生要差很多，明显不够流畅。

  • 内存消耗比较大。

这两个问题都源于WebView，它注定不会达到原生的体验。所以我们是否可以抛弃WebView，直接使用原生渲染？

JS引擎+原生渲染

2015年，Facebook发布了React Native。它是React在原生平台的延伸，支持Android和iOS。RN在语法层使用React技术栈来开发应用，在运行时通过JS引擎执行javascript，在渲染层使用原生组件绘制UI。这是一种全新的开发模式，旨在通过JS+原生渲染的方式，达到开发效率和渲染性能的最佳平衡。

代表技术：React Native、weex、NVue（Uniapp）

与RN不同的是，Weex和NVue则是使用Vue技术栈来开发原生渲染的应用。

这一类型的技术均是采用受限的React/Vue DSL + CSS规则子集 + Js引擎 + Bridge + 原生渲染引擎的架构方式。

原理

以RN为例。它的架构设计如下：

其中，绿色部分就是我们要写的代码。蓝色部分是RN提供的基础设施。黄色部分是Bridge。红色部分则是原生Api。

渲染

由于React本身只是一个js库，它通过虚拟DOM来抽象了对视图层的表达，所有的状态更新会引起虚拟DOM的变化，并通过renderer渲染器来将变化反映到真实UI的变更。在Web上那就是Dom的变更，使用react-dom包。在原生平台，那就是原生组件的变更，使用RN。

RN提供了一套针对原生的渲染器，维护着虚拟DOM与原生组件的映射。在开发时，我们仍然使用的是React + JSX + CSS。基础组件都是由RN提供。这些基础组件将和CSS一起，最终通过一个跨平台的Yoga渲染引擎渲染到原生UI上。

具体文档参考：官方文档。

底层Api

此外，RN还提供了许多的原生模块，来让开发者调用原生能力，从而实现各种偏底层的功能。

JS引擎

RN使用JavaScriptCore作为js引擎来执行js代码。RN的web端代码会被编译为js，它包含了react和rn的js依赖。并最终在JS引擎里被执行

Bridge

RN通过Bridge来支持js与原生之间的双向调用，它们使用JSON数据格式进行通信。其中包括要渲染的组件信息，或是调用底层Api的信息。都是通过Bridge实现的。

NVue的原理可以参考我之前写的文章。

限制

可以看到，JS引擎 + 原生渲染技术，由于是原生渲染，它解决了Hybrid在渲染性能上的诸多问题，用户体验上升了很多。但是，由于Js和原生是不共享内存的，所以它们需要借助Bridge传递JSON数据从而相互通信。那么Bridge就会直接的带来性能瓶颈：比如大量的JSON数据的传递、Bridge的调用频率的限制、异步通信带来的时间损耗等。渲染性能虽然得到了提升，但通信成本却增加了不少。

自渲染

2018年，Google发布了Flutter，它是一款自渲染的跨端框架。它与Hybrid和RN不同的是，它采用的是Dart语言作为开发语言。在生产环境下，Dart会被AOT编译为对应平台的动态库。所以它的执行效率要远高于js。同时，Flutter基于跨平台的Skia图形引擎自建了渲染引擎，组件的渲染不再需要通过Bridge通信，同时由于是自渲染，Flutter可以保证不同平台的渲染一执行。

代表技术：

原理

Flutter的官方架构图如下：

  • Embedder是OS的适配层，比如对于Android和iOS，有许多逻辑不一致，在这一层去做适配。它主要处理渲染Surface、线程设置、原生插件、打包设置等等。

  • Engine是引擎层，主要包含了Skia、Dart运行时。在这里Skia主要负责排版和渲染。Dart运行时，则为Dart语言提供执行和调用的能力。

  • Framework是框架层，这一层使用Dart语言实现的。主要包含了两套UI规范（Material和Cupertino）、各个基础的Widgets、还有动画、手势等基础设施。开发者将会使用框架层暴露的基础设施来开发应用程序。

限制

可见，Flutter的自渲染带来的好处还是挺多的，性能上、平台一致性上都很优秀。但有利也有弊，Dart语言对于Web开发者来说，还是有不少学习成本的。此外Flutter社区相比js和RN社区，生态还是差不少的。这也是一个开发者需要考虑的问题。

动态化也是一个问题。基于应用市场（AppStore）对动态应用程序的压制，Flutter目前已经关闭了动态更新的能力。当然，Flutter的底层其实是支持的，它的产物主要就是so动态库 + assets，完全支持动态修改。但是没有相应的api。（不过目前Android上有Hack的方法可以实现动态更新，iOS上是完全不行）。

自渲染还有一个问题就是，自渲染的UI是同层渲染的，会被绘制在SurfaceView上。对于原生来说，Flutter的UI都在一个View层级上。如果我们想实现原生View和Flutter View的分层，可能就实现不了了。比如想要让一个原生View显示在Flutter多个组件之间，覆盖下面的组件，并被上层的组件覆盖，这种不行。

小程序

小程序技术是出于商业目的被创造出来的，它的出现是各大巨头为了搭建自己的平台生态，构建服务闭环。以提升用户粘性和平台价值。小程序的出现，也确确实实为用户带来了巨大的便利。

从技术角度来讲，小程序技术也是一种跨平台方案。只需要按照小程序的DSL完成开发，就可以在多端的宿主App里面使用小程序。

代表技术：微信小程序、支付宝小程序、Uniapp的小程序引擎。

原理

小程序的架构通常是在Hybrid的基础上，做了渲染层和逻辑层的分离。如下的架构图：

可以看到，相比于Hybrid的架构，这里的架构，将逻辑层从WebView中移除，使用单独的js引擎来执行。这样做的目的是什么？是为了让逻辑层的代码执行不会卡住渲染。最明显的变化就是动画或者页面布局更加流畅。

实际开发过程中，往往小程序都会有自己的DSL和api。比如微信小程序使用的是自己定义的语言开发：js + wxml + wxss + wss，所有的api都通过wx.***暴露出来。而Uniapp则是使用vue开发。通过uni.***暴露api。

编译时

小程序和Uniapp的DSL不同，可能编译过程的细节处理也不尽相同。但大致上，在编译阶段，它们会将js和模版都编译到js中，模版转换为element的js对象。

运行时

在运行时，小程序和Uniapp都会有一个runtime，以供编译后的js执行期间调用api。同时，runtime也负责将element树通过JS bridge发送到渲染层，并执行渲染。当状态发生变更时，runtime也负责将更新后的element树，与原先的树进行diff，并将差异发送到渲染层进行渲染。

Uniapp使用Vue DSL，它的runtime很有可能是个魔改版的vue。小程序使用自己的DSL，runtime会基于自己的语法进行实现。可以想象为没有响应式，使用setData来更新的vue。

限制

和RN一样。逻辑层和渲染层分离带来的弊端就是数据通信存在性能问题。此外，渲染层仍然使用的是WebView渲染。而WebView的渲染性能始终是与原生存在一定的差距。

微信小程序新增了skyline渲染引擎，期望抛弃WebView渲染。旨在使用一种新的更高效的渲染管线，来带来更好的体验。

小程序跨应用

在各大巨头都推出了自己的小程序之后，市面上的小程序种类之多，已经达到了两位数。这时候许多开发者面临的问题已经不再是如何让自己的app跨多端，而是怎么让自己的小程序可以跨多个巨头应用。

这也催生了一些跨全平台的框架诞生：

框架UniappTaroMorJS
公司DCloud京东饿了么
DSLVue DSLReact/Vue DSL微信小程序DSL
支持平台全部小程序平台、H5、Android、iOS全部小程序平台、H5、RN全部小程序平台、H5

这三款框架都支持实现写一套代码，在任何小程序平台运行。

我们都知道各家小程序都有自己专属的DSL，在小程序开发完成后，需要经过各家自己的编译打包流程才能进行调试和发布市场。所以第三方框架想要实现小程序跨应用，基本就是要解决三个问题：

  1. 通过编译器将自己的DSL转成小程序的DSL。

  2. 通过运行时执行js逻辑，实现小程序的渲染。

  3. 对多家小程序的DSL适配。

可以看到，与App跨端相比，小程序跨应用还是相对来说比较简单。因为不需要提供js引擎，不需要提供渲染引擎，不需要提供基础组件，不需要提供api封装，这些都是由小程序平台提供的，三方框架更多的工作是转义。对于第3点，好在多家小程序的语法比较接近，适配工作也不是大头。接下来我们针对这三款框架分别讲述它们的实现原理。

【Uniapp】

Uniapp目前能力比较全，支持小程序、H5、App。App又支持vue、Nvue、uts...每一种DSL和编译target，它的实现都是不一样的。有兴趣的可以看我之前写的文章，讲述了App各种开发方式的原理，这里就不再赘述了。在这里只讲一下和小程序相关的原理。

编译器

Uniapp使用Vue DSL，它的编译器基于Webpack（Vue2）/Vite（Vue3）。在编译时，编译器会将.vue源码转换，并拆分为wxml、js、wxss、wxs等文件。

  • 源码转换：通过babel插件进行语法转换。如vue对象转为Page类、Page.json转换、模版语法转换（如v:if转为wx:if）等。各家小程序转换的工作不同。

  • 拆分：好在Vue的SFC本身就是模版、样式、脚本三者分离的。在转码后分别拆分为wxml、wxss、js。这个工作量还是比较小的。

运行时

Uniapp提供了一个runtime，运行在小程序运行时。它是一个mini版本的vue runtime。这是由于我们的代码语法和特性主要是对齐vue，所以我们的js需要vue runtime才能正确运行。

  • 支持vue特性：runtime包含mini vue，来支持我们开发时使用到的vue特性。比如计算属性、监听属性等。

  • 响应式状态更新：runtime对于响应式状态的变更，如this.count = 1，runtime需要转为调用setData，如this.setData({ count: 1 })。因为小程序只支持这种方式。

  • api转义：runtime需要对api调用进行转义，如uni.request需要转为调用wx.request，并对参数进行适配。

mpvue的原理可能与Uniapp类似，我还没有仔细分析过。

【Taro 2】

参考：Taro官方原理讲解

Taro 2和原理和Taro 3的原理完全不同！Taro 2采用React DSL开发，它的整体架构也是编译时 + 运行时。

编译时

同Uniapp一样，编译时需要做的工作主要也是语法转换。通过babel插件，转换代码为AST，再对AST进行一系列转换、修改。生成最后的小程序代码。

当然里面最复杂的工作就是jsx的转换。这是由于jsx是动态的，写法非常灵活，与模版语法不一样。比如：

if ... else ...         =>      wx:if wx:else
data.map(item => ...)   =>      wx:for="data" wx:for-item="item"
... && ...              =>      wx:if
复杂的表达式

因此Taro 2有大量的commit就用来fix各种情况下的jsx语法无法正确转换为wxml的bug。

运行时

Taro 2利用了React DSL，但实际上它的runtime和React没有任何关系，只是在开发阶段使用了React的语法。编译后class组件会是BaseComponent的实例。在组件内部调用的setState、forceUpdate等方法，已经被runtime重写为其他逻辑。

Taro的runtime js已经对setState、forceUpdate等React方法实现了重写，所以组件内部调用时并不会走React的方法。同时runtime还负责对接事件系统、生命周期函数等，与小程序对应功能对齐。

【Taro 3】

Uniapp和Taro 2都旨在强化编译时的转码来完成DSL到小程序的转换。而Taro 3则换了一种思路：就跟浏览器渲染网页主要依赖于BOM/DOM的Api一样。能否在小程序端也模拟出一套BOM/DOM的Api。这样的话，就不必纠结于使用React还是Vue开发了，因为它们最终还是调用BOM/DOM的Api，如appendChild、insertBefore等。

问题就在于小程序DSL通过声明式的模版语法定义节点树，通过setData方法触发更新。它并没有暴露原子操作最终元素的接口，那看起来就无法实现BOM/DOM的Api了？

模版化处理

小程序使用声明式的模版语法，使用到的组件都需要在模版里声明，它的动态性不强。但是有一个组件<template>，它有一个is属性，用来指定当前位置实际渲染的模版。这就让它变得很灵活了：

<!-- 声明一个具名的模版。模版名称用name指定 -->
<template name="fake_view">
    <!-- ... -->
</template>

<!-- 使用一个template模版，模版名称从item.nodeName动态获取 -->
<template is="{{ item.nodeName }}" data="{{ item }}" />

接下来想一想，我们已知整颗虚拟DOM树，我们怎么用&lt;template&gt;组件来渲染出实际的小程序模版？比如：

// 虚拟DOM树
const vnodeTree = {
    nodeName: "view",
    children: [{
        nodeName: "image",
        src: "xxxxx"
    }, {
        nodeName: "text",
        text: "xx"
    }]
}

// 期望渲染结果
<view>
    <image src="xxxxx" />
    <text>xx</text>
</view>

答案就是所有的小程序组件都声明一个template，template中v-for读取children，并且每一个item再根据item.type使用具体的template。这样的话，每一个组件都可以根据当前的虚拟DOM对象，动态的加载children组件。同时我们把所有小程序组件的所有属性也都定义到template中，这样组件的属性也可以根据虚拟DOM对象，动态设置了。如下：

<!-- view组件转换成template后 -->
<template name="tpl_view">
    <view
        id="{{ uid }}"
        class="{{ className }}"
        style="{{ style }}"
        hover-class="{{ hoverClass }}"
        hover-stop-propagation="{{ hoverStopPropagation }}"
        hover-start-time="{{ hoverStartTime || 50 }}"
        hover-stay-time="{{ hoverStayTime || 400 }}" >
        <block wx:for="{{children}}">
            <!-- 递归的根据nodeName动态使用另一个模版 -->
            <template is="{{ 'tpl' + item.nodeName }}" data="{{ item }]" />
        </block>
    </view>
</template>

这是一个view组件对应的模版，它的名称是"tpl_view"，这个过程就称为view组件的模版化处理，同理的，image组件和text组件等其他所有小程序组件，都可以进行同样的模版化处理。至此，整颗组件树就可以从根节点开始，递归的根据虚拟DOM对象渲染出来。我们的Page只需要定义一个data，wxml只需要定义一个根节点就行。

// js
Page({
    data: {
        root: { nodeName: "view", /* 其它属性... */, children: [/*  */] }
    }
})
// wxml
<template is="{{ 'tpl' + root.nodeName }}" data="{{ root }}" />

不得不说，这个设计非常的巧妙！利用&lt;template&gt;组件的动态性，完成了整颗树的动态处理！

mount的渲染就是如此。那更新呢？更简单了！由于我们的属性和children都已经完全动态化。我们只需要调用setData即可。比如：

this.setData({
    'root.children[0].src': 'xxxxxxx'
});

代表将root节点的第一个child的src属性设置为"xxxxxxx"。

封装BOM/DOM API

现在Taro已经通过模版化处理和虚拟DOM对象，实现了直接获取和设置树上的任意元素的属性和children。借此可以封装为BOM/DOM API。

Taro的taro-runtime包就是这套小程序的BOM/DOM API的实现。它构建了自己的Node、Element、Event对象。并提供了appendChild、insertBefore、removeChild等方法实现。

然后就是通过Webpack的ProvidePlugin插件，像小程序的逻辑层注入全局对象window、document。

new webpack.ProvidePlugin({
    'document': ['@tarojs/runtime', 'document'],
    'window': ['@tarojs/runtime', 'window'],
})

对接React

前面我们也说过，React本身不实际操作DOM，它操作的是虚拟DOM。renderer才会实际的去对应平台执行视图渲染。基于前面封装好的BOM/DOM API，其实就很容易写出一个Taro版本的renderer了，即taro-react。实际上主要就是两步：

  1. mount：实现ReactTaro.render函数，来挂载整颗树，类似于ReactDom.render。

  2. update：修改react-reconciler的HostConfig配置，让后续的协调更新，都走到taro-react包下的api。

对接Vue

Vue的架构虽然与React大相径庭。但Diff算法和更新逻辑其实是类似的。也是通过复写，来让Vue调用taro-runtime的api来mount和update视图。

编译时

Taro 3的这种技术方案，理论上来说编译时的工作量几乎没有了。因为它本质上就是将React/Vue运行在小程序上。所以完整的开发特性和代码都被保留下来了。

对比Taro 2的优势

  • 不限制DSL。可以使用React，也可以用Vue。开发的心智负担较小。

  • 模版动态构建。Taro 2通过编译生成wxml模版。Taro 3使用全组件的模版化处理，再结合&lt;template&gt;的动态特性，实现整个页面的递归动态构建。

  • 开发框架新特性无缝支持。React/Vue的功能不再受限，包括Hooks、Composition API等，都可以直接使用。

  • 社区维护更简单。React/Vue部分不用维护了，与官方对齐。只需要维护taro-runtime的包即可。在Taro 2时，还得大量维护React DSL以及jsx的转码。

性能问题

Taro 3的几乎全运行时的技术方案。可能会有人提出几个问题：引入React/Vue包导致小程序size增加；全运行时带来的性能压力。

  • Size问题：实际上，由于全组件的模版化处理，除了这些template，Taro 3不需要Page里的wxml。即Taro 3的wxml大小是有上限的。当项目页面达到一定程度后，Taro 2的wxml的体积将会超过Taro 3的size问题。

  • 运行时的性能：实际上taro-runtime的代码量很小，它使用小程序api操作视图。它的效率还是很高的。

【MorJS】

MorJS是一个使用微信小程序DSL来实现小程序跨应用的框架。它是在饿了么特定的技术背景下诞生的。前期，饿了么主要以微信小程序、支付宝小程序运营多年，大部分的存量业务都是使用微信小程序DSL或支付宝小程序DSL实现的。历史包袱很重，如果要改为其它DSL，改造成本巨大。MorJS也是使用编译时（重） + 运行时（轻）的解决方案。

编译时

静态编译主要处理js、wxml、wxss等文件中，属性兼容、模版兼容、配置兼容、生命周期兼容等工作，即抹平各家小程序之间的差异。

运行时

对一些无法在编译时静态处理的内容，MorJS选择在运行时处理。包括js Api、自定义组件等。

转H5

MorJS支持将小程序DSL转H5，转换后使用的是React语法，这个跟Uniapp和Taro正好相反，后者都是想方设法的将H5开发DSL转为小程序DSL。

也分为编译时 + 运行时：

  • 编译时：主要是将js、wxml、wxss合并为js文件，其中wxml转换为jsx，样式转换为css文件。

  • 运行时：要复杂很多，MorJS旨在模拟与小程序对等的运行环境来兼顾性能和体验。包含框架（Page、Component、生命周期函数）、组件（提供对等的基础组件）、API（类似于wx的api提供对等实现）、路由（Pages.json转路由配置）。

结语

跨端、跨平台是一个历史悠久的话题，为了应对各种业务场景，许许多多的开发团队都会有自己的尝试。本文所列举的框架和技术并不能穷举所有出现过的实现方案。当然，也没有哪一套方案，可以完美的满足所有需求。

对于未来的发展，我相信技术再怎么发展，它们基本的风向不会变。即朝着提升开发效率、提高交互性能、覆盖更多终端的方向前进。特别是在物联网的发展下，更多显示终端的出现，跨端的需求将会显得越来越重要！
